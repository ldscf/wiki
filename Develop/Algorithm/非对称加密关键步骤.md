SSL/TLS 是一种密码通信框架，是世界上使用最广泛的密码通信方法。SSL/TLS 综合运用了密码学中的对称密码、消息认证码、公钥、数字签名，随机数等，是密码学中的集大成者。

SSL(Secure Socket Layer)安全套接层，是 1994 年由 Netscape 公司设计的一套协议，并于 1995 年发布了 3.0 版本。

TLS(Transport Layer Security)传输层安全是 IETF 在 SSL 3.0 基础上设计的协议，实际上相当于 SSL 的后续版本。

### TLS 握手过程中非对称加密的关键步骤

实际上 TLS 握手过程非常复杂，涉及多个消息和可选步骤，但核心的非对称加密作用体现在以下几个关键阶段，以最常见的 RSA 密钥交换和数字证书为例：

前提：服务器已经拥有一个由受信任的 CA 签发的数字证书，该证书包含服务器的公钥，并且服务器保管着对应的私钥。客户端（浏览器）预装了许多受信任的根 CA 证书。

#### Client Hello (客户端发起请求)

客户端向服务器发送一个 "Client Hello" 消息。

此消息包含：
- 客户端支持的 TLS 版本（如 TLS 1.2, TLS 1.3）
- 客户端支持的加密套件列表（Cipher Suites）：这是一组加密算法的组合，包括密钥交换算法（如 RSA、DHE、ECDHE）、对称加密算法（如 AES-256-GCM）、哈希算法（生成会话密钥的伪随机函数 PRF 使用，如 SHA256）等
- 客户端生成的随机数 ClientRandom

实际上还会包括：当前时间、会话信息、可用的压缩方式清单等等。

#### Server Hello (服务器响应)

服务器接收到 "Client Hello" 后，从客户端提供的列表中选择它支持的最佳 TLS 版本和加密套件。

服务器发送一个 "Server Hello" 消息，其中包含：
- 选定的 TLS 版本和加密套件
- 服务器生成的随机数 ServerRandom
- 服务器的数字证书链：这就是非对称加密发挥作用的地方。服务器将它的实体证书（可能还包括一个或多个中间 CA 证书）发送给客户端

#### Certificate (服务器证书)

这是非对称加密的核心体现。 客户端接收到服务器的证书链后，开始验证服务器的身份：
- 验证证书的有效性：检查证书是否过期、是否被撤销（CRL/OCSP）、域名是否与访问的 URL 匹配等
- 验证证书的签名：客户端使用其预装的根 CA 证书，沿着证书链向上追溯，验证每个证书的数字签名。例如，客户端用中间 CA 的公钥验证服务器证书的签名，再用根 CA 的公钥验证中间 CA 证书的签名

信任建立：如果所有验证步骤都成功，客户端就信任了服务器证书中包含的公钥确实属于该服务器。这意味着客户端现在可以确信它正在与真实的服务器通信，而不是冒充者。

#### Client Key Exchange (客户端密钥交换)

这是使用非对称加密交换对称密钥的关键步骤。
- 客户端现在已经有了服务器的公钥（从已验证的证书中获取）
- 客户端生成一个随机的“预主密钥 (Pre-Master Secret, PMS)”，这个预主密钥是生成最终对称会话密钥的基础（之一，其他可能包括 ClientRandom、ServerRandom）
- 客户端使用服务器的公钥对这个“预主密钥”进行非对称加密
- 客户端将加密后的“预主密钥”发送给服务器

**为什么是公钥加密预主密钥？**
- 因为只有服务器拥有与该公钥对应的私钥，所以只有服务器才能解密这个“预主密钥”
- 即使是窃听者截获了加密的“预主密钥”和服务器的公钥，由于无法从公钥推导出私钥，窃听者也无法解密出真正的“预主密钥”，这保证了预主密钥的机密性

#### Server Decryption (服务器解密)

服务器接收到客户端发送的加密“预主密钥”后，使用自己的私钥对其进行非对称解密，从而获得原始的“预主密钥”。

#### 生成会话密钥 (后续对称加密的基础)

至此，客户端和服务器都拥有了以下信息：
- ClientRandom (客户端随机数)
- ServerRandom (服务器随机数)
- Pre-Master Secret (预主密钥)，48 字节（384 Bit）

双方各自独立地使用这些信息，通过一个确定性的伪随机函数 (PRF，参见：Client Hello中的哈希算法)，计算生成出相同的对称会话密钥 (Session Key)，用于后续所有数据的对称加密和解密。

P.S. 上面的三个随机数中，ClientRandom、ServerRandom 是可被获取的，PMS 因为在传输过程中使用“服务器公钥加密，所以只可被指定的服务器私钥解密。

TLS 协议的设计者通过组合三者来生成最终的会话密钥，是为了实现多重熵源和鲁棒性：
- ClientRandom 和 ServerRandom 确保了密钥生成过程中双方参与和新鲜度，防止会话被重放
- Pre-Master Secret 提供了最核心的秘密熵，承载着真正的秘密信息，必须通过非对称加密来安全地传输

#### Change Cipher Spec 和 Finished (握手完成)
- 双方发送 "Change Cipher Spec" 消息，表示后续通信将切换到加密模式
- 双方发送 "Finished" 消息，这是一个包含之前所有握手消息哈希值的加密消息，用于验证握手过程是否被篡改。这也是最后一次使用刚刚生成的对称会话密钥进行加密来验证握手完整性

### 密钥交换中的不同角色

#### 基于 RSA 的密钥交换 (RSA Key Exchange)
- 优势：简单直接。客户端用服务器的 RSA 公钥加密预主密钥，服务器用对应的 RSA 私钥解密
- 劣势：不提供前向保密 (Forward Secrecy)。如果服务器的私钥在未来某个时间被泄露，那么所有使用该私钥进行 RSA 密钥交换的旧会话（即使是已经结束的会话）都可能被解密。因为预主密钥直接用服务器公钥加密，而服务器公钥是固定的

#### 基于 Diffie-Hellman 或 Elliptic Curve Diffie-Hellman (DHE/ECDHE) 的密钥交换
- 优势：提供前向保密。在这种模式下，非对称加密（RSA 或 ECC）主要用于数字签名，而不是直接加密预主密钥
- 具体来说：客户端和服务器各自生成临时的 Diffie-Hellman (或 ECDH) 密钥对，并使用这些临时密钥对计算出会话密钥。然后，服务器使用其长期有效的私钥对自身的 DH/ECDH 公钥和握手消息进行数字签名。客户端使用服务器证书中的公钥验证这个签名，以确保 DH/ECDH 公钥确实来自真实的服务器，没有被篡改
- 由于每次会话都生成新的临时 DH/ECDH 密钥，即使服务器的长期私钥被泄露，也无法解密过去的会话数据，因为会话密钥不再依赖于长期私钥的机密性。这是现代 TLS 推荐和普遍采用的方法
