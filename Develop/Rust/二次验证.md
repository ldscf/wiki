基于 TOTP 的登录页面二次验证实现原理

### 概述

登录页面常见的二次验证流程：
- 用户输入用户名和密码
- 系统要求二次验证
- 用户打开 Authenticator APP，输入显示的 6 位数字
- 服务器验证通过后允许登录

首次配置时通常还会：
- 网站生成二维码
- 用户用 APP 扫描
- APP 保存 Secret，并根据 Secret 与当前时间生成验证码
- 用户输入一次验证码确认后，正式启用二次验证

这种机制称为 **TOTP**（Time-based One-Time Password，基于时间的一次性密码）。

Google Authenticator、Microsoft Authenticator、1Password、Bitwarden 等均支持标准 TOTP。个人开发者可自行实现，无需开发手机 APP，也无需购买短信服务。

#### 核心原理

服务器与手机 APP 共同拥有同一个 Secret。双方使用相同的 Secret、当前时间与 TOTP 算法，即可独立计算出相同的 6 位验证码，无需实时通信。

服务器和手机 APP

共同拥有同一个 Secret

        │

        ↓

   当前 Unix 时间

        │

        ↓

    TOTP 算法

        │

        ↓

     6 位数字

示例：

Secret: JBSWY3DPEHPK3PXP

当前时间：2026-08-18 09:35:12

计算结果：583921

手机显示 583921，服务器用相同 Secret 与时间重新计算，一致则验证成功。

#### 为什么不需要手机联网

配置阶段交换 Secret 后，生成验证码时手机无需联网。

时间通常按 30 秒划分窗口：

时间区间          Counter

09:35:00 ~ 09:35:29  100

09:35:30 ~ 09:35:59  101

09:36:00 ~ 09:36:29  102

本质可简化为：

counter = floor(current_unix_time / 30)

TOTP = HOTP(secret, counter)

手机与服务器各自用 Secret + 当前时间计算出相同结果即可完成验证。

#### 二维码的作用

配置时显示的二维码本质是包含标准化 URI 的普通二维码。

典型格式：

otpauth://totp/MyApp:adam?secret=JBSWY3DPEHPK3PXP&amp;issuer=MyApp

主要参数：

| 参数 | 含义 |
|:---|:---|
| otpauth | Authenticator 使用的 URI Scheme |
| totp | 表示使用 TOTP |
| MyApp:adam | 服务名称和账号 |
| secret | TOTP Secret |
| issuer | 服务提供方名称 |
APP 扫描后解析出 type、issuer、account、secret，并将 Secret 保存到安全存储。

### 应用

#### 配置流程

用户请求开启 2FA

        ↓

服务器随机生成 Secret

        ↓

生成 otpauth URI → 生成 QR Code → 显示二维码

        ↓

用户扫描 → APP 保存 Secret → 生成验证码

        ↓

用户输入验证码 → 服务器验证

        ├── 失败 → 不启用

        └── 成功 → 正式启用 2FA

**必须要求用户输入一次正确验证码后才启用。** 不能仅因二维码已显示就立即设置 mfa_enabled = true，否则可能出现用户未成功扫描但系统已启用的情况。

#### 登录流程

启用后登录变为：

用户名 + 密码 → 密码验证 → 是否启用 MFA？

        ↓ YES

要求输入 TOTP → 用户打开 APP 输入 6 位数字

        ↓

服务器验证 → 成功 → 创建 Session

形成双因素：
- 第一因素：Something You Know（密码）
- 第二因素：Something You Have（Authenticator APP 中的 TOTP）

#### 个人开发者是否需要开发手机 APP

**不需要。**

服务器只需实现：
- Secret 生成
- otpauth:// URI 生成
- QR Code 生成
- TOTP 验证
- MFA 状态管理
- Recovery Code 管理

手机端直接使用现有兼容 TOTP 的 APP（Google Authenticator、Microsoft Authenticator、1Password、Bitwarden、Authy 等）。

### 原理

#### 后端实现逻辑

以 Rust 为例，整体逻辑可抽象为：
1. secret = generate_secret()
2. uri = "otpauth://totp/MyApp:{username}?secret={secret}&amp;issuer=MyApp"
3. qr_code = generate_qrcode(uri)
4. code = request.code
5. verify_totp(secret, code)

实际项目中应使用经过验证的成熟密码学库，而非自行实现 TOTP 算法。重点关注正确性、边界条件、时间窗口、编码、常数时间比较与随机数质量。

#### Secret 的安全存储

密码应使用不可逆哈希（如 Argon2id），服务器不保存原始密码。

TOTP Secret 不能做不可逆哈希，因为验证时需要重新计算。应采用加密存储：

TOTP Secret → 加密 → Encrypted TOTP Secret → 数据库

验证时解密后使用。加密密钥应与数据库分离保存（KMS、Vault、Secret Manager、受保护环境变量等），避免与数据库中的 Secret 处于同一安全边界。

#### 时间误差处理

TOTP 通常以 30 秒为一个窗口。服务器与手机存在时钟偏差是正常现象，生产环境一般允许有限窗口（前一个、当前、后一个，即 T-30、T、T+30）。

窗口不宜过大，否则攻击者可利用的时间范围变长。服务器应通过 NTP 等机制保持正确系统时间。

#### 验证码必须限流

6 位验证码仅有 1,000,000 种可能，不能允许无限尝试。必须增加：
- 登录失败次数限制
- IP / 用户账号限速
- 短暂锁定与指数退避
- 安全日志

同时不应将用户输入的 TOTP 验证码写入日志。

#### Recovery Codes

启用 TOTP 时应同时生成 Recovery Codes，供用户丢失手机时使用。每个码：
- 只能使用一次
- 使用后立即失效
- 服务器只保存安全哈希
- 不写入明文日志

登录时可使用「密码 + TOTP」或「密码 + Recovery Code」。恢复机制本身必须严格保护，防止成为绕过 MFA 的入口。

Browser ──HTTPS──→ Authentication Service

                        │

          └─────────────┬─────────────┘

                        ↓

                     Database

手机端使用标准 Authenticator APP 生成验证码即可。

#### TOTP 与 Passkey / WebAuthn

TOTP 并非唯一的 MFA 方案。现代应用还可使用 WebAuthn / FIDO2 / Passkey。

TOTP 的主要弱点是易受实时钓鱼攻击（攻击者诱导用户输入验证码后立即转发）。WebAuthn / Passkey 抗钓鱼能力更强。

#### 推荐的 MFA 演进路线

普通个人项目：

Password + TOTP + Recovery Codes

已足够实用。

高价值系统（管理后台、云控制面、生产环境等）可进一步增加 Passkey / WebAuthn。两者可同时支持，用户可选择主认证方式并保留恢复机制。

#### 最小可行实现

快速可靠实现的核心范围：
- Generate Secret
- Generate otpauth URI
- Generate QR Code
- Verify Initial TOTP 并启用 MFA
- Login TOTP Verification
- Rate Limiting
- Recovery Codes
- Encrypt Secret
- Security Logging

关键原则：
- 不要自行设计 OTP 算法或二维码协议
- 不要自行开发 Authenticator APP
- 不要明文保存 TOTP Secret
- 不要无限允许验证码尝试
- 不要缺少 Recovery 机制

直接采用标准 TOTP 与 otpauth:// URI 即可。

### 结论

个人开发者完全可以实现登录页面的 APP + 6 位验证码二次验证。核心流程：

随机生成 Secret → 生成 otpauth:// URI → 生成二维码

        ↓

Authenticator APP 扫描并保存 Secret

        ↓

Secret + 当前时间 → TOTP → 6 位验证码

        ↓

服务器重新计算，一致则 MFA 验证成功

正常登录过程中服务器与手机甚至不需要直接通信。真正需要重点设计的是：
- Secret 的安全存储
- MFA 开启确认
- TOTP 时间窗口
- OTP 限速与暴力破解防护
- Recovery Codes
- Session 安全与 MFA 重置流程

普通个人项目使用 **Password + TOTP + Recovery Codes** 已是成熟、低成本的方案；高价值系统可在此基础上增加 WebAuthn / Passkey 以获得更强抗钓鱼能力。
