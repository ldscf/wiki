本条目讲解计算机系统中的 UTF-8 字符编码原理、汉字在不同编码规则中的字节占用差异以及在 MySQL 等工程环境中的陷阱。

### 字符集编码

汉字在不同字符集下的字节占用：

| 编码标准 | 类型 | 英文字符占用 | 常用汉字长度 | 生僻字 / Emoji | 备注 |
|:---|:---|:---|:---|:---|:---|
| GBK / GB2312 | 双字节扩展 (DBCS) | 1 字节 | 2 字节 | 2 字节 | 仅支持中日韩文字，不支持中文生僻古文字和 Emoji |
| UTF-8 | 多字节变长 | 1 字节 | 3 字节 | 4 字节 | 互联网标准，向下兼容 ASCII。欧洲、中东等字母文字为 2 字节 |
| UTF-16 | 定长 / 代理对 | 2 字节 | 2 字节 | 4 字节（代理对） | 内存与部分系统接口常用，不适合存储与网络传输 |
| MySQL utf8mb4 | 完整 UTF-8 实现 | 1 字节 | 3 字节 | 4 字节 | MySQL 首选，真正支持 Unicode 全集 |
| MySQL utf8 | 截断版 UTF-8 | 1 字节 | 3 字节 | 不支持 | 技术债产物，严禁在新系统中使用 |

### UTF-8 与 utf8mb4

有三个名词需要说清楚：UTF-8, utf8, utf8mb4。

根据 RFC 3629 规范，UTF-8 被定义为一种能够处理全部 Unicode 字符（从 $U+0000$ 到 $U+10FFFF$）的变长编码。

utf8mb4 的由来：2002 年 MySQL 开发人员在实现 UTF-8 字符集时，认为基本平面（BMP）内的 3 字节已经足够，为了优化存储效率，在代码里限制了最大字节长度为 3，然后他们将这个“阉割版”的 UTF-8 实现命名为 utf8。而到了 2010 年，随着 Emoji 和生僻字需求的爆发，官方意识到无法在原有的 utf8 命名下无损升级（会破坏现有的索引长度计算等逻辑），于是只能另起炉灶，实现了完整的 UTF-8，而且起了一个极具迷惑性的名字：utf8mb4。

#### MySQL 的 utf8 陷阱
- 现象：早期 MySQL 实现的 utf8 字符集最高仅支持 3 字节。
- 后果：存储 4 字节字符（如 “𠮷” 或 😂）时会触发 Incorrect string value 错误。
- 对策：utf8mb4（Most Bytes 4）是 MySQL 对官方 UTF-8 标准的补全。在现代工程实践中，必须统一使用 utf8mb4。

#### 变长逻辑与“𠮷”的特殊性
- 基本多文种平面 (BMP):码点范围 U+0000 到 U+FFFF。绝大多数汉字位于此平面，UTF-8 编码为 3 字节。
- 增补平面 (SP):码点超过 U+FFFF。例如“𠮷”（U+20BB7），在 UTF-8 中映射为 4 字节。
- 工程意义：“𠮷”常被用作系统是否完整支持 Unicode（对于 MySQL 即是否正确配置了 utf8mb4）的测试基准点。

# -*- coding: utf-8 -*-

def verify_encoding(char_name, character):

    print(f"--- 测试字符: {char_name} [{character}] ---")
    
    # 1. UTF-8 (标准互联网编码)

    utf8_bytes = character.encode('utf-8')

    print(f"UTF-8    字节数: {len(utf8_bytes)} | 字节序列: {utf8_bytes.hex(' ')}")
    
    # 2. GBK (中国标准扩展)

    try:

        gbk_bytes = character.encode('gbk')

        print(f"GBK      字节数: {len(gbk_bytes)} | 字节序列: {gbk_bytes.hex(' ')}")

    except UnicodeEncodeError:

        print(f"GBK      字节数: 无法编码 (GBK不包含此字符)")

    # 3. UTF-16 (内存常驻编码, 如 Java/C# 内部)

    utf16_bytes = character.encode('utf-16be') # 使用大端序方便观察

    print(f"UTF-16   字节数: {len(utf16_bytes)} | 字节序列: {utf16_bytes.hex(' ')}")
    
    # 4. 逻辑长度 (字符长度)

    print(f"字符数 (len): {len(character)}")

    print("\n")

if __name__ == "__main__":

    # 对比普通汉字与增补平面汉字

    verify_encoding("常用汉字", "吉")

    verify_encoding("生僻汉字", "𠮷")

### 参考

#### UTF-8 编码规则

UTF-8 (8-bit Unicode Transformation Format): 以 1 字节 (8 bits) 为最小编码单位。它是一种完全变长的编码，单个字符可能占用 1, 2, 3 或 4 个字节。自同步能力强 (任一字节丢失不影响后续解析)。对于超出基本平面 ($U+0000$ 到 $U+FFFF$) 的字符，通过特定的二进制前缀（如 11110xxx）来标识这是一个 4 字节字符。

# 吉 (e5 90 89): 首字节 e5 (二进制 11100101) 的前缀 1110 明确指示这是一个 3 字节 序列。

# 𠮷 (f0 a0 ae b7): 首字节 f0 (二进制 11110000) 的前缀 11110 明确指示这是一个 4 字节 序列。

#### UTF-16 的“代理对”

UTF-16 : 以 2 字节 (16 bits) 为最小编码单位，它也是变长的，字符占用 2 或 4 个字节。对于超出基本平面 ($U+0000$ 到 $U+FFFF$) 的字符，占用了两个 16 位的空闲空间（4 字节，高位代理和低位代理，代理对，Surrogate Pairs）表示一个生僻字。必须考虑字节序 (Endianness) (分为 BE 大端或 LE 小端)，自同步能力弱 (一旦错位，后续全部乱码)。

# “𠮷”的 UTF-16 序列：d8 42 df b7。由两个 16 位的“编码单元”组成（d842 和 dfb7）。在一些不支持非基本平面 (non-BMP) 的旧系统中，这两个单元会被误认为两个独立的字符，因此造成部分旧系统的代码统计“𠮷”的长度会返回 2。

### 工程应用

#### 数据库索引计算

在 utf8mb4 编码下，MySQL 在计算索引长度时会按最大字节数（4字节）预留空间：
* 若定义 VARCHAR(255)，其索引最大占用空间为：255 \times 4 = 1020 字节。
* 注意：Innodb 索引单列长度有限制（如 767 字节或 3072 字节），在大字段上建索引需注意长度溢出。

#### 截断安全 (Truncation)
* 风险：在非定长编码（UTF-8）中，直接按字节位（Byte Offset）截断可能切分一个完整汉字的内部字节，导致产生乱码序列。
* 规范：始终使用感知字符边界（Character-aware）的方法进行截取。

** *Python:* text[:n]

** *Java:* text.substring(0, n)

** *SQL:* LEFT(column, n)

#### 存储空间估算

虽然 UTF-8 存储汉字比 GBK 多出 50% 的空间，但具备以下优势：

# 兼容性：无缝支持多国语言，避免乱码。

# 压缩友好：在开启 HTTP Gzip 或数据库压缩后，两者的实际存储/传输差异会大幅缩小。

### FAQ
* Q: UTF8mb4 既然支持 4 字节，那存普通汉字是不是也变大了？

** A: 不会。UTF-8 是变长的，普通汉字依然占 3 字节，只有遇到需要 4 字节的特殊字符时才会按 4 字节存储。
* Q: 为什么编程语言里的 length 有时和字节对不上？

** A: 因为 length 通常统计的是字符数（或者 UTF-16 的 Code Unit），而有些函数统计的是字节数。
* Q: UTF-16 比 UTF-8 省空间？

** A: 在 UTF-16 中，绝大多数亚洲文字（基本平面内）固定占用 2 字节，而在 UTF-8 中则需要 3 字节。  

结论： 如果是一本纯中文的离线电子书，UTF-16 的体积通常比 UTF-8 小约 33%（或者说 UTF-8 体积比 UTF-16 大约 50%）。
