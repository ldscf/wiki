在数据库的世界里，索引扮演着至关重要的角色，是决定数据库性能、响应速度和扩展能力的核心基石。简单来说，如果将数据库表比作一本字典，那么索引就是这本字典的“检字表”，可以迅速定位到字词所在的页码。

索引通常以牺牲一定的存储空间和 DML（插入、更新、删除）操作性能为代价，换取查询性能的巨大飞跃。在任何一个专业的数据库应用中，对索引的深刻理解和战略性使用，是区分普通数据库管理员与资深数据库性能专家的关键所在。

### 术语

#### 基数

基数(Cardinality)是衡量列中数据唯一性的一个关键指标。
1. 高基数 (High Cardinality)：列中包含大量不同的、几乎不重复的值。例如，表中的主键列、身份证号码列或电子邮箱列。高基数是 B-Tree 索引最理想的应用场景，因为索引可以快速定位到极少数甚至唯一的行，选择性（Selectivity）极高。
1. 低基数 (Low Cardinality)：列中包含的唯一值很少，数据存在大量重复。例如，性别列（男、女）、状态标志列（Y/N）或产品分类列。对于低基数列，标准的 B-Tree 索引效率不高，因为索引扫描后仍需访问大量包含相同值的数据行。在这种情况下，位图索引 (Bitmap Index) 是更优的选择，它为每个不同的键值创建一个位图，其中每个位对应一个数据行的 ROWID，能够高效地处理低基数列的复杂组合查询。

#### 聚簇因子

聚簇因子(Clustering Factor)是衡量索引键值的排列顺序与表中数据行物理存储顺序之间关联性的指标。它记录在 DBA_INDEXES 视图中。
1. 理想情况（低聚簇因子）：如果索引中顺序相邻的条目所指向的数据行在物理上也大致相邻，那么聚簇因子就会很低，接近于表所占用的数据块数。这意味着当进行索引范围扫描时，Oracle 可以用很少的 I/O 读取到所有需要的表数据块，效率极高。
1. 糟糕情况（高聚簇因子）：如果索引条目的顺序与数据行的物理存储顺序完全不匹配（随机分布），那么聚簇因子就会很高，接近于表的总行数。这意味着即使是小范围的索引扫描，也可能需要访问大量离散的、遍布在整个表中的数据块，导致大量的 I/O 操作。此时，Oracle 优化器可能会放弃使用该索引，转而选择全表扫描。

高聚簇因子是索引效率低下的一个常见原因，有时比索引高度或删除的叶节点更能说明问题。通过对表进行重组（例如，CREATE TABLE ... AS SELECT ... ORDER BY ...）可以改善聚簇因子。

#### 已删除的叶节点

从表中执行 DELETE 操作时，Oracle 为了提升删除操作的性能，并不会立即从索引中物理移除对应的条目并重新整理索引结构。相反，它会将该索引条目标记为“逻辑删除”状态。
1. 工作机制：这些被逻辑删除的节点（或称为“死”节点）会暂时保留在索引的叶块中。这样做的好处是避免了因少量删除就频繁地进行索引块的合并和树结构的再平衡，从而显著加快了 DELETE 命令的执行速度。
1. 空间重用：这些被标记为删除的索引空间在后续的 INSERT 操作中可以被重新利用。当一个新的值需要插入到该索引块时，Oracle 可以清理这些已删除的条目并插入新条目。
1. 性能影响：如果一个表经历了大量的删除操作，但后续插入操作很少或者插入的值无法利用这些已删除的空间（例如，索引在一个单调递增的序列上，删除的都是旧数据），那么索引中会累积大量无法回收的“死”空间。这会导致索引变得“臃肿”，扫描效率降低。通常，当已删除的叶节点占总叶节点数量的 20% 以上时，就应该考虑重建索引。
1. 监控：通过 ANALYZE INDEX ... VALIDATE STRUCTURE 命令并查询 INDEX_STATS 视图来获取这一信息。

#### 索引高度与深度

索引高度和深度(Height and B-Level)描述的是 B-Tree 索引的层级结构。
1. 索引高度 (Height)：指从根节点到叶节点所经过的层数。一个设计良好的 B-Tree 索引通常非常“扁平”。
1. 深度 (BLEVEL)：在 Oracle 的数据字典视图 DBA_INDEXES 或 USER_INDEXES 中，BLEVEL 列精确地表示了索引的深度（Branch Level），即从根块到叶块的级别。根节点的 BLEVEL 为 0。

一个高度为 3 的 B-Tree 索引已经可以轻松支持数百万条记录的快速查找。当 BLEVEL 达到或超过 4 时，通常意味着索引结构可能变得不再高效，每次索引扫描都需要更多次的 I/O 操作。这通常是重建索引的一个强烈信号。

#### 逻辑读取数

每次索引访问的逻辑读取数 (Logical Reads per Access)这是衡量索引效率的一个重要性能指标，指的是通过索引检索单条记录所需的逻辑 I/O（也称为“一致性获取” - consistent gets）次数。
1. 逻辑读取 vs. 物理读取：逻辑读取是从 Oracle 的数据缓冲区（Buffer Cache）中读取数据块，它未必会触发磁盘的物理 I/O，因为请求的数据块可能已经被缓存。然而，过高的逻辑读取次数依然会消耗大量的 CPU 资源，并可能间接导致物理 I/O 增加。
1. 评估标准：一个健康的索引，其访问的逻辑读取数应该很低。虽然没有一个绝对的硬性规定，但业界通常认为，如果每次索引访问的逻辑读取数持续 大于 10，就表明索引可能存在碎片化或结构不良的问题，此时应考虑进行索引重建。这个值很大程度上受到 聚簇因子 (Clustering Factor) 的影响。

### 索引类型
1. B-Tree 索引 (B-Tree Index)：默认类型，适用于高基数列和大部分查询场景。
1. 组合索引 (Composite Index)：在两个或更多列上创建的索引。列的顺序至关重要，应将最常用于 WHERE 子句且选择性最高的列放在前面。
1. 位图索引 (Bitmap Index)：适用于低基数列，在数据仓库环境中对复杂查询（多个 AND, OR, NOT 条件）有奇效。但在 OLTP（在线事务处理）系统中，由于其在 DML 操作时锁定机制较为复杂，应谨慎使用。
1. 函数索引 (Function-based Index)：可以对基于列的函数或表达式的结果创建索引。例如，可以为 UPPER(last_name) 创建索引，以加速不区分大小写的查询。
1. 反向键索引 (Reverse Key Index)：将索引列的值在存入索引前进行按字节反转。它对于解决在单调递增（如序列生成）的列上进行大量并发插入时产生的“右侧索引块争用”问题非常有效。

### 重建索引

关于是否以及何时重建索引，普遍接受的说法是避免不必要的定期重建，重建索引是一个需要谨慎对待的操作。重建索引是一个 I/O 密集型和 CPU 密集型的操作，会占用大量的磁盘 I/O、内存和处理器资源，可能导致数据库服务器在重建期间变慢，影响其他正常的业务查询，极易造成数据库性能瓶颈。而且现代数据库管理系统在日常操作中已经非常擅长管理索引，碎片化程度通常不会达到需要重建的地步。重建一个碎片化程度不高的索引，不仅浪费资源，而且效果微乎其微。
```
 ALTER INDEX index_name REBUILD [ONLINE];
 # 使用 ONLINE 选项（企业版功能）可以在重建过程中允许对基表进行 DML 操作，从而最大限度地减少对业务的影响。
```

强烈建议重建索引的信号包括：

# 索引深度 (BLEVEL) \>= 4：表明索引层级过多。
1. 高比例的已删除叶节点：例如，DEL_LF_ROWS / LF_ROWS > 0.2，且这部分空间确认无法被重用。
1. 极高的聚簇因子：导致索引范围扫描效率极低。
1. 索引因批量加载或维护操作而变为 UNUSABLE 状态。
1. 为回收大量碎片化空间：在对表进行了大规模的数据归档或删除之后。

在决定重建前，应首先分析索引的统计信息（DBA_INDEXES, INDEX_STATS）和相关 SQL 的执行计划，确认索引碎片确实是性能瓶颈。
